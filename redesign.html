EI-FEATURE-SERVICE

特征只定义一次，接入任何腔室都按同一口径计算

ei-feature-service 是一个特征计算服务：把分析中验证有效的特征上传为“特征包”，特征包按 run_id 自己取数、自己计算；接入新腔室时，只需在腔室绑定里依次选择机台、腔室、配方和特征；每个结果都能追溯来源。

定义一次，多腔室复用

特征包里的 fetch 按 run_id 取数，compute 只管计算。接入新腔室时，只需在腔室绑定里勾选配方和特征。

结果可重现

取数和计算分成两个函数，compute 是纯函数。填一个真实 run_id 就能试跑一次；同一版本、同样的 data，结果完全一致。

每个值可追溯

每个特征值都关联一个计算批次，能查到 run_id、特征版本、绑定修订号，以及是否被重算过。

整体架构

ei-feature-service 负责计算，GDE 负责数据与存储

调用方通过 REST API 使用 ei-feature-service。ei-feature-service 通过 GDE SDK 注册订阅；每个执行结束后，GDE 往 Redis 写一条只含 run_id 的通知，计算引擎监听 Redis，再通过 SDK 按 run_id 拉取数据。MinIO、PostgreSQL、ClickHouse 和 Redis 都是 GDE 提供的基础能力。

特征管理上传、自动检查、评审发布、下线
腔室绑定按机台 → 腔室 → 配方选择要算的特征；规则可导入导出；审核通过后生效，保存全部修订
调度管理绑定审核通过后经 SDK 注册订阅；监听 Redis 通知并分发计算；补算、重算
计算引擎调用 fetch(run_id) 经 SDK 取数、compute(data) 计算，结果写入 PostgreSQL；支持单次试跑
机台、腔室、配方清单：Web 控制台直接请求 GDE 元数据服务获取，不经过 ei-feature-service。ei-feature-service 只在提交绑定时经 SDK 校验腔室和配方是否存在。
使用流程

从上线一个特征到查看结果

    这些操作对应的接口
    
  
    控制台的每个操作都调用下面的接口，Agent 和下游系统也直接使用它们。请求、响应、错误码的完整定义见第 4 页“实现规格”。
    
  
    
  
    
  
    方法路径作用
    
  
    POST/api/features上传特征包，自动检查通过后生成草稿
    
  
    POST/api/features/{id}/{version}/submit提交评审，内容锁定
    
  
    POST/api/features/{id}/{version}/review评审：approve 发布，或 reject 附意见退回
    
  
    POST/api/features/{id}/{version}/retire下线：从所有腔室绑定中移除，历史值保留
    
  
    POST/api/features/{id}/{version}/trial试跑：传 run_id，执行一次 fetch + compute，返回取到的数据概要和结果；不写入特征值
    
  
    GET/api/features、/api/features/{id}/{version}特征列表（可按 status、关键字筛选）/ 详情（含代码）
    
  
    DELETE/api/features/{id}/{version}删除草稿（仅本人）
    
  
    GET/api/chamber-bindings绑定规则列表，可按 tool、chamber、recipe、feature、status 筛选
    
  
    POST/api/chamber-bindings/{chamber}提交腔室绑定（控制台根据选择自动生成），生成待审核修订
    
  
    POST/api/chamber-bindings/{chamber}/revisions/{rev}/review审核绑定修订：approve 生效并经 SDK 同步订阅，或 reject 附意见退回
    
  
    POST/api/chamber-bindings/{chamber}/revisions/{rev}/withdraw提交人撤回待审核修订
    
  
    GET/api/chamber-bindings/export导出规则：按筛选条件导出生效修订的绑定 JSON
    
  
    POST/api/chamber-bindings/import导入规则：校验后按腔室各生成一个待审核修订；dry_run=true 只校验不落库
    
  
    POST/api/schedules/{chamber}/pause、/resume暂停或恢复该腔室的计算（经 SDK 暂停 / 恢复订阅）
    
  
    POST/api/batches按腔室、特征、时间范围补算（fill）或重算（overwrite）
    
  
    GET/api/values按机台、腔室、配方、特征、晶圆、时间查询特征值
    
  
    GET/api/batches、/api/batches/{batch_id}批次列表 / 某个计算批次的来源信息
    
  
    POST/api/batches/{batch_id}/cancel取消排队中或进行中的补算、重算
    
  
    GET/api/schedules各腔室的订阅、生效修订、处理进度
    
  
    REDISgde:run:done计算引擎以消费组监听的执行结束通知：含 run_id、机台、腔室、配方、晶圆、结束时间，不含数据

    1. 技术栈
    
  
    
    
    部分选型
    
    
    语言Python 3.11

    部署一个镜像，两个进程：api（uvicorn）和 worker（python -m ei_feature_service.worker），可分别扩副本

    4. 接口通用约定
    
  
      
    
    • 前缀 /api，请求、响应都是 JSON（上传特征包除外）。时间一律 ISO 8601 带时区；日期参数为 YYYY-MM-DD，按 EIF_TZ 解释，to 包含当天。
      • 
    
    • 用户：网关注入请求头 X-User（工号）。所有写接口必需，缺失返回 401。保留用户名 system 只能由服务自己使用。
      • 
    
    • 列表：参数 page（从 1 开始）、page_size（默认 20，最大 200；/api/values 最大 1000），响应 {"items": [...], "total": 123, "page": 1, "page_size": 20}。
      • 
    
    • 错误：响应体 {"code": "BINDING_INVALID", "message": "人能看懂的说明", "details": {...}}。
      • 
    
    • 特征引用：字符串 "{feature_id}@{version}"，如 gas_flow_diffmean@1.0.0。
      • 
  
    
  
    
    
    错误码HTTP场景
    
    
    UNAUTHENTICATED401缺少 X-User
    
    
    FORBIDDEN403评审 / 审核人与提交人相同；撤回别人的修订
    
    
    NOT_FOUND404特征、修订、批次不存在
    
    
    INVALID_STATE409当前状态不允许该操作（details 带 status）
    
    
    VERSION_EXISTS / VERSION_NOT_INCREASING409版本已存在；新版本不大于已有最大版本
    
    
    PENDING_EXISTS409该腔室已有待审核修订
    
    
    NO_CHANGE409提交内容与生效修订相同
    
    
    PACKAGE_INVALID422特征包校验失败，details.errors: [{"file", "line", "message"}]
    
    
    BINDING_INVALID422绑定校验失败，details.errors: [{"path", "message"}]，path 如 rules[1].recipes[0]
    
    
    VALIDATION_ERROR422其他参数错误（Pydantic）
    
    
    TRIAL_REQUIRED422评审通过时 trial_runs 为空
    
    
    GDE_UNAVAILABLE502调用 GDE SDK 失败；本次操作不落库
    
  
    

  
    5. 接口定义
    
  
    下面用 Python 类型写模型，字段名即 JSON 字段名；? 表示可为 null 或可省略。
    

    schemas（共用模型）
    

    class Feature:
    feature_id: str; version: str
    status: Literal["draft", "review", "published", "retired"]
    description: str; unit: str?          # 取自 spec.desc、spec.output.unit
    spec: dict; package_hash: str
    created_by: str; created_at: datetime; submitted_at: datetime?
    published_by: str?; published_at: datetime?
    retired_by: str?; retired_at: datetime?; retire_reason: str?
    review_log: list[ReviewEntry]

class ReviewEntry:
    decision: Literal["approve", "reject"]; reviewer: str; comment: str?
    trial_runs: list[str]; at: datetime

class Rule:
    recipes: list[str]                    # 至少 1 个
    features: dict[str, str]              # feature_id -> version，至少 1 个

class BindingSpec:
    tool: str; chamber: str; rules: list[Rule]

class Revision:
    chamber: str; revision: int; tool: str; spec: BindingSpec
    status: Literal["pending", "active", "rejected", "withdrawn", "superseded"]
    source: Literal["console", "api", "import", "system"]
    base_revision: int?; gde_sub_id: str?
    created_by: str; created_at: datetime
    reviewed_by: str?; reviewed_at: datetime?; review_note: str?; superseded_at: datetime?

class Batch:
    batch_id: int; mode: Literal["live", "fill", "overwrite"]
    status: Literal["queued", "running", "done", "failed", "cancelled"]
    chamber: str; binding_revision: int; features: list[str]?
    data_from: datetime; data_to: datetime; reason: str?; superseded_by: int?
    run_total: int; value_ok: int; value_null: int; error: str?
    created_by: str; created_at: datetime; started_at: datetime?; finished_at: datetime?

class Value:
    feature_id: str; version: str; run_id: str
    tool: str; chamber: str; recipe: str; lot: str?; wafer: str?; run_end_at: datetime
    value: float?; reason: str?; reason_detail: str?; batch_id: int; computed_at: datetime
    retired: bool                         # 由 feature.status == "retired" 得出
    

  
    
    
    接口请求响应与规则
    
    
    POST /api/featuresmultipart/form-data：spec=feature.json 文件，code=compute.py 文件201 Feature（status=draft，created_by=X-User）。按第 7 节校验；先写 MinIO 再插库，插库失败时删除已写对象。
    
    
    GET /api/featuresstatus? q?（匹配 id 或 desc，ILIKE）feature_id? page page_size列表 Feature，按 feature_id、版本（语义化排序）降序。
    
    
    GET /api/features/{id}/{version}—Feature + code: str（compute.py 内容）。
    
    
    POST …/{version}/submit—仅 draft、仅 created_by 本人。→ review，写 submitted_at。返回 Feature。
    
    
    POST …/{version}/review{"decision": "approve"|"reject", "comment": str?, "trial_runs": [str]}仅 review；reviewer ≠ created_by（403）。approve 要求 trial_runs 非空（422 TRIAL_REQUIRED）→ published，写 published_by/at；reject 要求 comment 非空 → draft。两种都向 review_log 追加一条。
    
    
    POST …/{version}/retire{"reason": str}仅 published。在一个事务里执行第 6 节“下线”步骤。返回 {"feature": Feature, "affected": [{"chamber", "new_revision", "subscription": "kept"|"cancelled"}]}。
    
    
    POST …/{version}/trial{"run_id": str}draft / review / published 可用。在沙箱执行一次，不写库。返回 {"run": {"run_id","tool","chamber","recipe","lot","wafer","end_at"}, "data_summary": {key: {"points": int, "t_min": float, "t_max": float}}, "value": float?, "reason": str?, "reason_detail": str?, "fetch_ms": int, "compute_ms": int}。data_summary 只对 fetch 返回值中形如 {"t": [...], "v": [...]} 的顶层键生成。
    
    
    GET /api/chamber-bindingstool? chamber? recipe? feature?（id 或 id@version）status?（active / pending）{"items": [{"tool", "chamber", "active": Revision?, "pending": Revision?}]}，不分页。recipe、feature 通过 binding_item 过滤生效修订。“未绑定”腔室后端不知道，由前端用 GDE 元数据补齐。
    
    
    GET /api/chamber-bindings/{chamber}revision?不带 revision：{"chamber", "revisions": [Revision]}，新的在前；带 revision：单个 Revision。
    
    
    POST /api/chamber-bindings/{chamber}BindingSpec + base_revision?201 Revision（pending，source=console 或 api：请求头 X-Client: console 时为 console）。按第 6 节“绑定校验”；路径 chamber 必须等于 body.chamber。recipes 按 GDE 返回的顺序保存。
    
    
    POST …/revisions/{rev}/review{"decision": "approve"|"reject", "comment": str?}仅 pending；审核人 ≠ created_by。reject 需 comment → rejected。approve 见第 6 节“绑定生效”。返回 Revision。
    
    
    POST …/revisions/{rev}/withdraw—仅 pending、仅 created_by 本人 → withdrawn。
    
    
    GET /api/chamber-bindings/export同列表筛选参数导出文件（Content-Disposition: attachment; filename=ei-feature-service-bindings.json）：{"format": "ei-feature-service.bindings/v1", "exported_at", "bindings": [{"tool","chamber","revision","rules"}]}，只含生效修订。
    
    
    POST /api/chamber-bindings/importdry_run（默认 true）；body 为导出格式{"items": [{"tool","chamber","action": "new"|"skip"|"conflict"|"error","message","revision"?, "errors"?}]}。每个腔室独立按“绑定校验”判断：有待审核 → conflict；与生效修订一致 → skip；文件内同一腔室重复 → error。dry_run=false 时在一个事务里为所有 new 插入 pending 修订（source=import，base_revision=当前生效修订号）；有 error 时也只导入 new 的部分。
    
    
    GET /api/schedulestool? chamber?[{"tool","chamber","gde_sub_id","binding_revision","feature_count","status": "running"|"paused"|"cancelled"|"unknown","progress": datetime?}]。status 经 SDK 查询（失败时为 unknown，不报错）；progress = 该腔室最近一个 live 批次中最大的 run_end_at。
    
    
    POST /api/schedules/{chamber}/pause、/resume—调 SDK 暂停 / 恢复生效修订上的 gde_sub_id。无订阅 → 409 INVALID_STATE。
    
    
    POST /api/batches{"chamber", "mode": "fill"|"overwrite", "features": [str], "from": date, "to": date, "reason": str}201 Batch（queued）。features 必须都在该腔室生效修订中；from ≤ to ≤ 今天；天数 ≤ EIF_BATCH_MAX_DAYS；reason 必填。binding_revision 取当前生效修订。
    
    
    GET /api/batches、/api/batches/{id}chamber? mode? status?列表按 batch_id 降序 / 单个 Batch。
    
    
    POST /api/batches/{id}/cancel—仅 queued / running 的 fill、overwrite → cancelled；BatchRunner 在处理下一个 run_id 前检查状态并停止，已写入的值保留。
    
    
    GET /api/valuesfeature（必填，id@version）tool? chamber? recipe? wafer? lot? from? to? only_null?列表 Value，按 run_end_at 升序。
    
  
    

  
    6. 状态机与关键事务
    
  
    
  
    
  
    特征 feature.status
    

    draft     --submit(本人)--------------> review
review    --review approve(他人)-------> published
review    --review reject(他人, 意见)---> draft
published --retire(原因)---------------> retired
# draft 可重新上传同版本？不可以：同一 (id, version) 只能上传一次，
# 被退回后改代码需要上传新版本号。draft 允许删除：
# DELETE /api/features/{id}/{version}（仅 draft、仅本人，同时删 MinIO 对象）
    
  
    
  
    
  
    绑定修订 chamber_binding.status
    

    (新建)  --------------------------> pending
pending --approve(他人)-------------> active   # 原 active → superseded
pending --reject(他人, 意见)--------> rejected
pending --withdraw(本人)------------> withdrawn
pending --所含特征被下线(system)----> withdrawn
active  --新修订生效----------------> superseded
# source=system 的修订直接以 active 插入，不经过 pending
    
  
    
  
    

  
    绑定校验（提交、导入共用，全部错误一次返回）：
    
  
      
    
    1. 经 SDK 查询：chamber 存在且属于 tool；每个 recipe 属于该 chamber。
      2. 
    
    2. rules 至少 1 条；每条 recipes、features 都至少 1 个；同一 chamber 内 recipe 不重复。
      3. 
    
    3. 每个 features 项对应的 (feature_id, version) 存在且 status=published。
      4. 
    
    4. 该 chamber 没有 pending 修订（否则 PENDING_EXISTS）；规范化后（recipes 排序、rules 保持顺序）与生效修订 spec 相同则 NO_CHANGE。
      5. 
  
    
  
    新修订号 = 该 chamber 现有最大 revision + 1（在事务里 SELECT … FOR UPDATE 锁住该 chamber 的行，或用 advisory lock hashtext(chamber)）。插入 chamber_binding 的同一事务里按 spec 展开写 binding_item（rule_no 从 1 开始）。
    

  
    绑定生效（approve）：
    
  
      
    
    1. 读当前 active 修订 A（可能没有）和待审核修订 P。
      2. 
    
    2. 调 SDK：A 没有 gde_sub_id → subscribe(tool, chamber, recipes(P)) 得到 sub_id；有且 recipes 集合变化 → update_subscription(sub_id, recipes(P))；没变化 → 不调用。SDK 失败 → 502，什么都不改。
      3. 
    
    3. 事务：A.status=superseded、A.superseded_at=now()；P.status=active、reviewed_by/at、review_note、gde_sub_id=sub_id。
      4. 
    
    4. 如果事务失败而第 2 步是新注册，调用 cancel_subscription(sub_id) 回滚（失败只记日志）。
      5. 
  
    

  
    下线（retire，一个事务）：
    
  
      
    
    1. feature.status=retired，写 retired_by/at、retire_reason。
      2. 
    
    2. 用 binding_item 找出 active 修订中含该 (id, version) 的腔室。对每个腔室：从 spec 删掉该特征，删除变空的规则；把该腔室的 pending 修订置为 withdrawn，review_note=“特征 {ref} 下线，自动撤回”；插入新修订（source=system，status=active，created_by=system，reviewed_by=system）；旧 active → superseded。
      3. 
    
    3. 新修订没有规则时：调用 SDK cancel_subscription，新修订的 gde_sub_id 置空；配方集合变了则 update_subscription。SDK 调用放在事务提交后执行，失败写入 outbox 日志并由 worker 每分钟重试（实现为一张简单的表 gde_outbox(id, action, payload jsonb, attempts, last_error, created_at, done_at)）。
      4.

    上传校验（packaging/validate.py，全部错误一次返回）：
    
  
      
    
    • feature.json：合法 JSON；id 匹配 ^[a-z][a-z0-9_]{2,63}$；version 匹配 ^\d+\.\d+\.\d+$；desc 1~200 字；output.unit 字符串，最长 32。其他键原样保存。

      •

      •

      • 
    
    • package_hash = sha256(feature.json 字节 + b"\n" + compute.py 字节)。

    src/eifeature/__init__.py 对外接口
    

    class Skip(Exception):
    def __init__(self, reason: str): ...   # reason 匹配 ^[A-Z][A-Z0-9_]{2,31}$，否则视为 COMPUTE_ERROR

class Series:                          # 不可变
    t: list[float]                       # 相对执行开始的秒数，升序
    v: list[float]
    def steps(self, *step_ids: int) -> Series      # 只保留这些步骤时间段内的点，t 改为相对第一个所选步骤开始
    def window(self, t0: float, t1: float) -> Series  # 保留 t0 ≤ t ≤ t1
    def __len__(self) -> int

class Run:
    run_id, tool, chamber, recipe: str; lot, wafer: str | None
    start_at, end_at: datetime
    steps: list[Step]                    # Step(id: int, start_s: float, end_s: float)

class gde:                             # 模块，只能在 fetch 中调用；在 compute 中调用抛 RuntimeError
    def run_info(run_id: str) -> Run
    def trace(run_id: str, signal: str, unit: str | None = None) -> Series
        # 信号不存在抛 Skip("MISSING_SIGNAL")；单位换算由 SDK 完成，不支持的单位抛 Skip("BAD_UNIT")

class ops:                             # 参数接受 Series 或 {"t": [...], "v": [...]}
    def dedup(s) -> Series               # 去掉重复时间戳，保留第一个
    def resample(s, hz: float) -> Series # 线性插值到等间隔
    def despike(s, window_s: float, sigma: float) -> Series  # 滑动中位数 + MAD，超出 sigma 的点替换为中位数
    def slope(s) -> Series               # 相邻点差分 / 时间差
    def mean(s) -> float; def std(s) -> float   # 总体标准差；空序列抛 Skip("EMPTY_SERIES")
    
  
    fetch 返回的 dict 在同一子进程里直接传给 compute，不做序列化。compute 必须返回有限的 float（int 转成 float），否则记 COMPUTE_ERROR。

    def resume_subscription(self, sub_id: str) -> None

    def trace(self, run_id: str, signal: str, unit: str | None, timeout_s: float) -> Series

    9. 计算引擎
    

    RunResult（沙箱返回）与原因码映射
    

    RunResult(value: float | None, reason: str | None, reason_detail: str | None,
          data_summary: dict, fetch_ms: int, compute_ms: int)

fetch 抛 Skip(r)              -> reason = r
fetch 抛 GdeNotFound          -> reason = "MISSING_DATA"
fetch 抛 GdeUnavailable       -> 不写结果，交给上层重试（计入熔断）
fetch 超过 FETCH_TIMEOUT_S    -> reason = "FETCH_TIMEOUT"
fetch 抛其他异常              -> reason = "FETCH_ERROR",   reason_detail = 异常类型 + 消息（截断 1 KB）
compute 抛 Skip(r)            -> reason = r
compute 超时 / 异常 / 非有限数 -> reason = "COMPUTE_ERROR", reason_detail 同上
子进程被杀（总超时）          -> reason = "FETCH_TIMEOUT" 或 "COMPUTE_ERROR"（看卡在哪一步）
    


    engine/live.py · LiveConsumer（每个 worker 进程一个）
    

    启动：XGROUP CREATE {stream} {group} $ MKSTREAM（已存在忽略 BUSYGROUP）
循环：
  msgs = XREADGROUP GROUP {group} {consumer} COUNT 32 BLOCK 5000 STREAMS {stream} >
  每 60 秒额外执行一次：XAUTOCLAIM {stream} {group} {consumer} {CLAIM_IDLE_S*1000} 0-0 COUNT 32
  对每条消息并发处理（受信号量约束）：
    m = 解析字段 run_id, tool, chamber, recipe, wafer?, lot?, end_at, sub_id?
    缺字段 -> 记日志，XACK，结束
    rev = 该 chamber 的 active 修订；没有 -> XACK，结束
    feats = binding_item 中 (chamber, rev, recipe) 的全部特征；空 -> XACK，结束
    batch = 取或建实时批次(chamber, rev, end_at 所在整点)          # 见下
    for f in feats:
        已存在 feature_value(f.id, f.version, run_id) -> 跳过           # 去重
        async with 全局信号量, 腔室信号量(chamber), 熔断器:
            r = await sandbox.run(package(f), run_id)
        GdeUnavailable -> 本条消息不 ACK（留给重试），继续下一条消息
        写 feature_value（INSERT … ON CONFLICT DO NOTHING），并更新批次计数
    全部特征写完 -> XACK
  投递次数（XPENDING 中的 times_delivered）> MAX_DELIVERIES 的消息：
    对未写结果的特征写 reason="FETCH_ERROR"、reason_detail="max deliveries exceeded"，然后 XACK
    
  
      
    
    • 实时批次：键 (chamber, binding_revision, data_from=整点)。用唯一部分索引 ON feature_batch (chamber, binding_revision, data_from) WHERE mode='live' 配合 INSERT … ON CONFLICT DO NOTHING 再查询来取或建；created_by=system，status=running，data_to=data_from+1h。LiveBatchCloser 每 5 分钟把 data_to 早于 now()−10 分钟的 running 实时批次置为 done、写 finished_at。
      • 
    
    • 计数：写入一个值后 UPDATE feature_batch SET value_ok = value_ok + 1（或 value_null）；run_total 在一条消息的所有特征处理完后 +1。
      • 
    
    • 熔断：连续 BREAKER_FAILURES 次 GdeUnavailable 后，BREAKER_PAUSE_S 秒内所有取数直接视为 GdeUnavailable；任何一次成功清零。
      • 
    
    • 特征包加载：按 (id, version) 从 MinIO 下载到 /tmp/ei-feature/pkgs/{id}/{version}/，校验 package_hash 后缓存；子进程用 importlib 以唯一模块名加载 compute.py，并按 (id, version) 缓存模块对象。

    engine/batch.py · BatchRunner（每个 worker 进程一个，取补算 / 重算任务）
    

    循环（每 5 秒）：
  b = SELECT … FROM feature_batch WHERE status='queued' ORDER BY batch_id
      LIMIT 1 FOR UPDATE SKIP LOCKED
  没有 -> 等待
  b.status='running', started_at=now()
  rev = chamber_binding(b.chamber, b.binding_revision)
  runs = gde.list_runs(b.chamber, recipes(rev), b.data_from, b.data_to)
  for run in runs:                                   # 每处理一个 run 前重新读 b.status，cancelled 则停止
      for f in b.features 中、且 run.recipe 在 rev 里对应该特征的规则内:
          fill：已有 feature_value -> 跳过
          async with 全局信号量, 补算信号量, 腔室信号量, 熔断器:
              r = sandbox.run(...)
          GdeUnavailable -> 退避重试 3 次（5s/20s/60s），仍失败则 b.status='failed'、b.error，结束
          fill：INSERT … ON CONFLICT DO NOTHING
          overwrite：同一事务内 DELETE (f, run_id) 再 INSERT，batch_id=b.batch_id
  overwrite 完成后：把同腔室、时间重叠、特征有交集、未被覆盖的旧批次 superseded_by=b.batch_id
  b.status='done', finished_at=now(), run_total=len(runs)
    
  
    试跑在 api 进程内执行：同一个 sandbox.run，受 EIF_TRIAL_CONCURRENCY 信号量限制，超时与原因码规则相同，结果直接返回不写库。

    12. 测试与验收
    
  
    
    
    范围必须覆盖
    
    
    特征包校验每条校验规则至少一个通过、一个失败用例；版本递增判断（1.0.10 > 1.0.9）。

    LiveConsumer（集成，真 Redis + FakeGdeClient）同一消息投递两次只写一次；GdeUnavailable 不 ACK、认领后重试成功；超过投递上限写 FETCH_ERROR；配方不在绑定内直接 ACK；实时批次按整点归并。
    
    
    BatchRunnerfill 跳过已有值；overwrite 覆盖并标记旧批次 superseded_by；cancel 生效；两个 worker 不会领同一个批次。
