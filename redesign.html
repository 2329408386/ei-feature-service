EI-FEATURE-SERVICE

特征只定义一次，接入任何腔室都按同一口径计算

ei-feature-service 是一个特征计算服务：把分析中验证有效的特征登记下来，每个特征下挂一个或多个“算子”（一段按 run_id 自己取数、自己计算的代码），算子可以随时增加、各自评审；接入时只需在算子绑定里选 recipe：GDE 按 recipe 推送它在所有机台 / 腔室上的执行，以后新增的腔室也自动计算；每个结果都能追溯到算子版本。

定义一次，多腔室复用

算子里的 fetch 按 run_id 取数，compute 只管计算。接入新腔室时，只需在算子绑定里选 recipe、勾选腔室。

结果可重现

取数和计算分成两个函数，compute 是纯函数。填一个真实 run_id 就能试跑一次；同一版本、同样的 data，结果完全一致。

每个值可追溯

每个特征值都关联一个计算批次，能查到 run_id、特征版本、绑定修订号，以及是否被重算过。

整体架构

ei-feature-service 负责计算，GDE 负责数据与存储

调用方通过 REST API 使用 ei-feature-service。ei-feature-service 通过 GDE SDK 注册订阅；每个执行结束后，GDE 往 Redis 写一条只含 run_id 的通知，计算引擎监听 Redis，再通过 SDK 按 run_id 拉取数据。MinIO、PostgreSQL、ClickHouse 和 Redis 都是 GDE 提供的基础能力。

特征管理特征和算子直接填 JSON / 代码，自动检查、评审发布、下线；特征里可随时新增算子，同名算子自动升版本
算子绑定只选 recipe（不选机台 / 腔室）：GDE 按 recipe 推送全部腔室的执行；可导入导出；审核通过后生效，保存全部修订
调度管理绑定审核通过后经 SDK 注册订阅；监听 Redis 通知并分发计算；补算、重算
计算引擎调用 fetch(run_id) 经 SDK 取数、compute(data) 计算，结果写入 PostgreSQL；支持单次试跑
机台、腔室、配方清单：Web 控制台直接请求 GDE 元数据服务获取，不经过 ei-feature-service。ei-feature-service 只在提交绑定时经 SDK 校验腔室和配方是否存在。

      GET/api/features
      
  
      

  
      这些操作对应的接口
      
  
      控制台的每个操作都调用下面的接口，Agent 和下游系统也直接使用它们。请求、响应、错误码的完整定义见第 4 页“实现规格”。
      
  
      
  
      
  
      方法路径作用
      
  
      POST/api/features新增特征（直接提交 feature.json），自动检查通过后生成草稿
      
  
      POST/api/features/{id}/{version}/submit、/review特征提交评审 / 评审（不需要试跑）；新版本发布时旧版本自动下线
      
  
      POST/api/features/{id}/{version}/retire整个特征下线：已发布的算子一起下线并移出绑定，历史值保留
      
  
      GET/api/features、/api/features/{id}/{version}特征列表（可按机台类型筛选）/ 详情（含该特征的全部算子）
      
  
      PATCH/api/features/{id}、/api/operators/{fid}/{name}修改特征的名称、机台类型 / 算子的名称；ID 不变，对全部版本生效，不需要评审
      
  
      POST/api/operators在特征下新增算子（operator.json + 代码 + 可选文件名）；同名算子再次提交自动升版本，特征版本不变
      
  
      POST/api/operators/{fid}/{name}/{ver}/submit、/review算子提交评审 / 评审（通过前至少试跑 1 个 run_id）
      
  
      POST/api/operators/{fid}/{name}/{ver}/trial试跑：传 run_id，执行一次 fetch + compute，返回数据概要和结果；不写入特征值
      
  
      POST/api/operators/{fid}/{name}/{ver}/retire算子下线：从绑定中移除，历史值保留
      
  
      GET/api/operators、/api/operators/{fid}/{name}/{ver}算子列表 / 详情（含代码）；DELETE 删除本人草稿
      
  
      GET/api/gde/*GDE 元数据转发：绑定页面用 recipes?q=（模糊搜索）、recipes/{recipe}/chambers（只读展示覆盖的机台和腔室）；试跑选执行用 fleets、fleets/{fleet}/chambers、chambers/{chamber}/recipes、runs
      
  
      GET/api/bindings算子绑定列表，可按 feature_id、operator、recipe、status 筛选
      
  
      POST/api/bindings/{feature_id}/{operator}提交算子绑定（控制台根据选择自动生成），生成待审核修订
      
  
      POST/api/bindings/{feature_id}/{operator}/revisions/{rev}/review审核绑定修订：approve 生效并同步 recipe 订阅，或 reject 附意见退回
      
  
      POST/api/bindings/{feature_id}/{operator}/revisions/{rev}/withdraw提交人撤回待审核修订
      
  
      GET/api/bindings/export导出：按筛选条件导出生效修订的绑定 JSON
      
  
      POST/api/bindings/import导入：校验后按算子各生成一个待审核修订；dry_run=true 只校验不落库
      
  
      POST/api/schedules/{recipe}/pause、/resume暂停或恢复该 recipe 的计算（经 SDK 暂停 / 恢复订阅，作用于全部腔室）
      
  
      POST/api/batches按 recipe、算子、时间范围补算（fill）或重算（overwrite），覆盖该 recipe 下全部腔室
      
  
      GET/api/values按算子引用，以及机台、腔室、recipe、晶圆、时间查询特征值
      
  
      GET/api/batches、/api/batches/{batch_id}批次列表 / 某个计算批次的来源信息
      
  
      POST/api/batches/{batch_id}/cancel取消排队中或进行中的补算、重算
      
  
      GET/api/schedules以 recipe 为键：订阅状态、同步状态、绑定的算子、跑过它的机台 / 腔室及各自处理进度
      
  
      REDISgde:run:done计算引擎以消费组监听的执行结束通知：含 run_id、机台、腔室、配方、晶圆、结束时间，不含数据
      
  
      
  
      

      




      
  实现规格
  
      照着这一页就能写出代码
      
  
      本页把前三页的设计落到工程细节：技术栈、目录、配置、接口的请求与响应、状态机、GDE SDK 适配层、计算引擎的处理流程、前端页面和验收标准。前三页（含各页“设计说明”弹窗里的 schema.sql）与本页一起构成完整规格；两处不一致时以本页为准。
      

  
      1. 技术栈与运行方式
      
  
      
    
      部分选型
      
    
      语言Python 3.12
      
    
      依赖管理uv；依赖全部用 == 固定版本，uv.lock 提交到仓库
      
    
      WebFastAPI + Pydantic v2，uvicorn 由 main.py 在代码里启动
      
    
      数据库PostgreSQL + SQLAlchemy 2.0（async）+ psycopg 3；不用迁移工具，建表 SQL 在启动时执行
      
    
      Redis / MinIOredis-py（Stream + 消费组）；minio
      
    
      沙箱pebble 进程池（单任务超时可杀子进程）
      
    
      测试pytest + pytest-asyncio + httpx + fakeredis
      
    
      前端单独的仓库，不放在本仓库；页面规格见第 11 节
      
  
      
  
      运行：在根目录执行 uv sync 后 uv run main.py。一个进程同时提供 REST API 和后台计算（监听 Redis、补算重算、实时批次收尾、同步 recipe 订阅），不需要 Dockerfile，也不需要单独的 worker 进程。启动时依次：读 config/config.json → 执行 src/model/schema.sql（全部 IF NOT EXISTS，重复执行无副作用）→ 启动后台任务 → 启动 uvicorn。多实例部署时直接多起几个，消费组和 FOR UPDATE SKIP LOCKED 保证不重复处理。

      main.py
      

      from contextlib import asynccontextmanager
import uvicorn
from fastapi import FastAPI
from src.util.config import settings
from src.util import db, errors
from src.api import features, operators, bindings, gde, schedules, batches, values
from src import engine

@asynccontextmanager
async def lifespan(app):
    await db.init_schema()        # 执行 src/model/schema.sql
    tasks = engine.start()        # live、batch_runner、jobs
    yield
    await engine.stop(tasks)

app = FastAPI(title="ei-feature-service", lifespan=lifespan)
errors.install(app)
for m in (features, operators, bindings, gde, schedules, batches, values):
    app.include_router(m.router, prefix="/api")

if __name__ == "__main__":
    uvicorn.run(app, host=settings.server.host,
                port=settings.server.port)

      4. 接口通用约定
      
  
        
    
      • 前缀 /api，请求、响应都是 JSON（特征、算子也直接提交 JSON，不再上传文件）。时间一律 ISO 8601 带时区；日期参数为 YYYY-MM-DD，按 TZ 解释，to / end 包含当天。
        • 
    
      • 用户：网关注入请求头 X-User（工号）。所有写接口必需，缺失返回 401。保留用户名 system 只能由服务自己使用。
        • 
    
      • 列表：参数 page（从 1 开始）、page_size（默认 20，最大 200；/api/values 最大 1000），响应 {"items": [...], "total": 123, "page": 1, "page_size": 20}。
        • 
    
      • 错误：响应体 {"code": "BINDING_INVALID", "message": "人能看懂的说明", "details": {...}}。
        • 
    
      • 特征引用："{feature_id}@{version}"，如 gas_flow_diffmean@1.0.0（特征版本是语义化版本）。
        • 
    
      • 算子引用："{feature_id}/{operator}@{version}"，如 gas_flow_diffmean/diffmean@2（算子版本是从 1 开始的整数）。绑定、批次、特征值都按算子引用。
        • 
  
      
  
      
    
      错误码HTTP场景
      
    
      UNAUTHENTICATED401缺少 X-User
      
    
      FORBIDDEN403评审 / 审核人与提交人相同；撤回别人的修订；删除别人的草稿
      
    
      NOT_FOUND404特征、算子、修订、批次、run_id、fleet、腔室、recipe 不存在
      
    
      INVALID_STATE409当前状态不允许该操作（details 带 status）；如特征未发布时发布算子（status=unpublished）、特征已整体下线后再加算子
      
    
      VERSION_EXISTS / VERSION_NOT_INCREASING409特征版本已存在；新版本不大于已有最大版本
      
    
      CODE_FILE_EXISTS409同一特征下已有同名的算子代码文件
      
    
      PENDING_EXISTS409该算子已有待审核的绑定修订
      
    
      NO_CHANGE409提交内容与生效修订相同
      
    
      SPEC_INVALID422feature.json / operator.json / 代码校验失败，details.errors: [{"file", "line", "message"}]；file 为 feature.json、operator.json、code_file 或代码文件名
      
    
      BINDING_INVALID422绑定校验失败，details.errors: [{"path", "message"}]，path 如 recipes[1].chambers[0]
      
    
      VALIDATION_ERROR422其他参数错误（Pydantic），包括算子引用格式不对
      
    
      TRIAL_REQUIRED422算子评审通过时 trial_runs 为空
      
    
      GDE_UNAVAILABLE502同步调用 GDE 失败（试跑、绑定校验、元数据转发、暂停 / 恢复）；本次操作不落库

      6. 状态机与关键事务
      
  
      
  
      
  
      特征 feature.status、算子 operator.status
      

      draft     --submit(本人)--------------> review
review    --review approve(他人)-------> published
review    --review reject(他人, 意见)---> draft
published --retire(原因)---------------> retired
# 特征：approve 时同 feature_id 旧的 published → retired（被替代）；
#       手动 retire 表示整个特征下线，全部 published 算子一起下线
# 算子：approve 需 trial_runs 非空，且特征已有 published 版本
# 两者都不能重复提交同一版本；draft 可由本人删除
      
  
      
  
      
  
      绑定修订 operator_binding.status
      

      (新建)  --------------------------> pending
pending --approve(他人)-------------> active   # 原 active → superseded
pending --reject(他人, 意见)--------> rejected
pending --withdraw(本人)------------> withdrawn
pending --所绑算子版本被下线(system)--> withdrawn
active  --新修订生效----------------> superseded
# source=system 的修订直接以 active 插入，不经过 pending
      
  
      
  
      

  
      新增算子（POST /api/operators，一个事务，advisory lock feature:{feature_id}）：校验 → 查特征存在且未整体下线 → version = max(version) + 1 → 确定 code_file 并查重 → 写 MinIO（features/{fid}/operators/{name}/{version}/operator.json 和 {code_file}）→ 插入 operator。operator.json 按键排序、缩进 2 序列化后存储；code_hash = sha256(operator.json 字节 + b"\n" + 代码字节)。
      

  
      绑定校验（提交、导入共用，全部错误一次返回）：
      
  
        
    
      1. (feature_id, operator, version) 对应的算子存在且 status=published（错误 path=version）。
        2. 
    
      2. recipes 至少 1 个；去掉首尾空白后非空、不重复（错误 path=recipes[i]）。
        3. 
    
      3. 经 SDK recipe_chambers(recipe) 反查 recipe 存在（GdeNotFound → “recipe 不存在”）。不选、也不校验机台 / 腔室。
        4. 
    
      4. 该算子没有 pending 修订（否则 PENDING_EXISTS）；规范化后（recipe 去空白、排序去重，只保留 feature_id、operator、version、recipes 四个键）与生效修订 spec 相同则 NO_CHANGE。
        5. 
  
      
  
      新修订号 = 该算子现有最大 revision + 1（advisory lock binding:{feature_id}/{operator}）。同一事务里按 spec 展开写 binding_item（每个 recipe 一行，带算子 version）。
      

  
      绑定生效（approve，一个事务）：
      
  
        
    
      1. P 所绑算子版本仍为 published（否则 409）。
        2. 
    
      2. 当前 active 修订 A（可能没有）→ superseded；P → active，写 reviewed_by/at、review_note。
        3. 
    
      3. 对 A、P 涉及的全部 recipe 执行“订阅重算”。
        4. 
    
      4. 事务提交后对这些 recipe 执行“订阅同步”。同步失败不影响审核结果，记在 recipe_subscription.last_error，由后台任务重试。
        5. 
  
      

  
      订阅重算（在调用方事务里，按 recipe 排序依次 advisory lock sub:{recipe}）：wanted = 是否有 active 修订的 binding_item 含该 recipe；写入 recipe_subscription.wanted（不存在则插入）。
      
  
      订阅同步（src/service/subscription.py，事务外）：GDE 按 recipe 订阅，订阅后自动推送该 recipe 在所有机台 / 腔室上的执行（包括以后新增的腔室），本服务不维护腔室清单。对每个 recipe SELECT … FOR UPDATE SKIP LOCKED，若 wanted 与“是否有 gde_sub_id”不一致：wanted 且无订阅 → subscribe(recipe)；不 wanted 且有订阅 → cancel_subscription，gde_sub_id 置空。成功写 synced_at，清空 attempts、last_error；失败 attempts+1、记 last_error。src/engine/jobs.py 每 60 秒对全部未同步的 recipe 执行一次。
      

  
      算子下线（retire，一个事务）：
      
  
        
    
      1. operator.status=retired，写 retired_by/at、retire_reason。
        2. 
    
      2. 该算子的 pending 修订若绑定的正是此版本 → withdrawn，review_note=“算子 {ref} 下线，自动撤回”。
        3. 
    
      3. 该算子的 active 修订若绑定的正是此版本：其余 pending 修订也撤回；A → superseded；插入 recipes 为空的新修订（source=system，status=active，created_by=reviewed_by=system）；对 A 涉及的 recipe 执行“订阅重算”。
        4. 
    
      4. 提交后执行“订阅同步”（没有算子要算的 recipe 会被取消订阅）。
        5. 
  
      

  
      名称与机台类型（src/service/meta.py）：ID（feature_id、算子名）永远不变，引用、绑定、特征值都按 ID。可修改的显示名称和机台类型存在 feature_meta（按 feature_id）、operator_meta（按 feature_id + 算子名），与版本无关、修改不需要评审；不写进 feature.json / operator.json。列表和详情接口把它们填进 display_name / tool_type，关键字搜索也匹配显示名称。

      src/eifeature 对外接口
      

      class Skip(Exception):
    def __init__(self, reason: str): ...   # reason 匹配 ^[A-Z][A-Z0-9_]{2,31}$，否则视为 COMPUTE_ERROR

class Series:                          # 不可变
    t: list[float]                       # 相对执行开始的秒数，升序
    v: list[float]
    def steps(self, *step_ids: int) -> Series      # 只保留这些步骤时间段内的点，t 改为相对第一个所选步骤开始
    def window(self, t0: float, t1: float) -> Series  # 保留 t0 ≤ t ≤ t1
    def __len__(self) -> int

class Run:
    run_id, tool, chamber, recipe: str; lot, wafer: str | None
    start_at, end_at: datetime
    steps: list[Step]                    # Step(id: int, start_s: float, end_s: float)

class gde:                             # 模块，只能在 fetch 中调用；在 compute 中调用抛 RuntimeError
    def run_info(run_id: str) -> Run
    def trace(run_id: str, signal: str, unit: str | None = None) -> Series
        # 信号不存在抛 Skip("MISSING_SIGNAL")；单位换算由 SDK 完成，不支持的单位抛 Skip("BAD_UNIT")

class ops:                             # 参数接受 Series 或 {"t": [...], "v": [...]}
    def dedup(s) -> Series               # 去掉重复时间戳，保留第一个
    def resample(s, hz: float) -> Series # 线性插值到等间隔
    def despike(s, window_s: float, sigma: float) -> Series  # 滑动中位数 + MAD，超出 sigma 的点替换为中位数
    def slope(s) -> Series               # 相邻点差分 / 时间差
    def mean(s) -> float; def std(s) -> float   # 总体标准差；空序列抛 Skip("EMPTY_SERIES")
      
  
      fetch 返回的 dict 在同一子进程里直接传给 compute，不做序列化。compute 必须返回有限的 float（int 转成 float），否则记 COMPUTE_ERROR。

    def run_info(self, run_id: str) -> Run
    def trace(self, run_id: str, signal: str, unit: str | None, timeout_s: float) -> Series

# 所有方法失败时抛 GdeUnavailable（网络、5xx、超时）或 GdeNotFound（run / 信号 / fleet / 腔室 / recipe 不存在）。
# SDK 是同步库：在 async 代码中通过 asyncio.to_thread 调用。
# FakeGdeClient：FLEET-ETCH-A = ETCH-01（CH-A01、CH-A02），FLEET-ETCH-B = ETCH-02（CH-B02）；元数据不区分时间范围，list_runs 不返回晚于当前时间的执行。
      

  
      9. 计算引擎
      

      RunResult（沙箱返回）与原因码映射
      

      RunResult(value: float | None, reason: str | None, reason_detail: str | None,
          data_summary: dict, fetch_ms: int, compute_ms: int)

fetch 抛 Skip(r)              -> reason = r
fetch 抛 GdeNotFound          -> reason = "MISSING_DATA"
fetch 抛 GdeUnavailable       -> 不写结果，交给上层重试（计入熔断）
fetch 超过 FETCH_TIMEOUT_S    -> reason = "FETCH_TIMEOUT"
fetch 抛其他异常              -> reason = "FETCH_ERROR",   reason_detail = 异常类型 + 消息（截断 1 KB）
compute 抛 Skip(r)            -> reason = r
compute 超时 / 异常 / 非有限数 -> reason = "COMPUTE_ERROR", reason_detail 同上
子进程被杀（总超时）          -> reason = "FETCH_TIMEOUT" 或 "COMPUTE_ERROR"（看卡在哪一步）
      


      src/engine/live.py · LiveConsumer（每个实例一个）
      

      启动：XGROUP CREATE {stream} {group} $ MKSTREAM（已存在忽略 BUSYGROUP）
循环：
  msgs = XREADGROUP GROUP {group} {consumer} COUNT 32 BLOCK 5000 STREAMS {stream} >
  每 60 秒额外执行一次：XAUTOCLAIM {stream} {group} {consumer} {CLAIM_IDLE_S*1000} 0-0 COUNT 32
  对每条消息并发处理（受信号量约束）：
    m = 解析字段 run_id, tool, chamber, recipe, wafer?, lot?, end_at, sub_id?
    缺字段 -> 记日志，XACK，结束
    ops = 所有 active 修订的 binding_item 中该 recipe 对应的算子版本（与腔室无关）；空 -> XACK，结束
    batch = 取或建实时批次(recipe, end_at 所在整点)                  # 见下
    for op in ops:
        已存在 feature_value(op.feature_id, op.name, op.version, run_id) -> 跳过   # 去重
        async with 全局信号量, 腔室信号量(chamber), 熔断器:
            r = await sandbox.run(op, run_id)
        GdeUnavailable -> 本条消息不 ACK（留给重试），继续下一条消息
        写 feature_value（INSERT … ON CONFLICT DO NOTHING），并更新批次计数
    全部算子写完 -> XACK
  投递次数（XPENDING 中的 times_delivered）> MAX_DELIVERIES 的消息：
    对未写结果的算子写 reason="FETCH_ERROR"、reason_detail="max deliveries exceeded"，然后 XACK
      
  
        
    
      • 实时批次：键 (recipe, data_from=整点)。用唯一部分索引 ON feature_batch (recipe, data_from) WHERE mode='live' 配合 INSERT … ON CONFLICT DO NOTHING 再查询来取或建；created_by=system，status=running，data_to=data_from+1h。src/engine/jobs.py 每 5 分钟把 data_to 早于 now()−10 分钟的 running 实时批次置为 done、写 finished_at。
        • 
    
      • 计数：写入一个值后 UPDATE feature_batch SET value_ok = value_ok + 1（或 value_null）；run_total 在一条消息的所有算子处理完后 +1。
        • 
    
      • 熔断：连续 BREAKER_FAILURES 次 GdeUnavailable 后，BREAKER_PAUSE_S 秒内所有取数直接视为 GdeUnavailable；任何一次成功清零。
        • 
    
      • 算子加载：按 (feature_id, name, version) 从 MinIO 下载 operator.json 和 code_file 到 {PACKAGE_CACHE_DIR}/{feature_id}/{name}/{version}/{code_hash[:12]}/，校验 code_hash 后缓存；子进程用 importlib 以唯一模块名（含 hash）加载代码文件并缓存模块对象。沙箱入参为 OperatorRef(feature_id, operator, version, code_hash, code_file)。
        • 
  
      


      src/engine/batch_runner.py · BatchRunner（每个实例一个，取补算 / 重算任务）
      

      循环（每 5 秒）：
  b = SELECT … FROM feature_batch WHERE status='queued' ORDER BY batch_id
      LIMIT 1 FOR UPDATE SKIP LOCKED
  没有 -> 等待
  b.status='running', started_at=now()
  ops = 按 b.operators 读出算子的 code_hash、code_file
  runs = gde.list_runs(b.recipe, b.data_from, b.data_to)    # 该 recipe 在全部腔室上的执行
  for run in runs:                                   # 每处理一个 run 前重新读 b.status，cancelled 则停止
      for op in ops:
          fill：已有 feature_value -> 跳过
          async with 全局信号量, 补算信号量, 腔室信号量(run.chamber), 熔断器:
              r = sandbox.run(...)
          GdeUnavailable -> 退避重试 3 次（5s/20s/60s），仍失败则 b.status='failed'、b.error，结束
          fill：INSERT … ON CONFLICT DO NOTHING
          overwrite：同一事务内 DELETE (op, run_id) 再 INSERT，batch_id=b.batch_id
  overwrite 完成后：把同 recipe、时间重叠、算子有交集（operators ?| …，live 批次视为全部）、未被覆盖的旧批次 superseded_by=b.batch_id
  b.status='done', finished_at=now(), run_total=len(runs)
      
  
      试跑在处理请求的同一进程内执行：同一个 sandbox.run，受 TRIAL_CONCURRENCY 信号量限制，超时与原因码规则相同，结果直接返回不写库。

      12. 测试与验收
      
  
      
    
      范围必须覆盖
      
    
      提交校验feature.json、operator.json、code_file、代码每条规则至少一个通过、一个失败用例；特征版本递增判断（1.0.10 > 1.0.9）；同名算子版本自动 +1、默认文件名、文件名重复 409。
      
    
      eifeaturesteps / window 边界；dedup、resample、despike、slope、mean、std 与手算结果一致（误差 1e-9）。
      
    
      沙箱第 9 节原因码映射表每一行；死循环被杀；compute 中调用 gde 报错。
      
    
      状态机第 6 节每条转移的允许 / 拒绝，包括本人评审 403、本人审核 403、他人撤回 403；新特征版本发布时旧版本自动下线；特征未发布时算子不能发布。
      
    
      绑定校验各条（算子未发布、recipe 不存在 / 为空 / 重复）；approve 后按 recipe 订阅重算与同步（subscribe / cancel）；GDE 不可用时审核照样生效、后台重试后同步；导入的 new / skip / conflict / error；同一 recipe 在新腔室上的执行也会计算。
      
    
      GDE 元数据/api/gde/*：fleet 腔室默认时间范围、recipe 模糊过滤与 limit、recipe 反查、腔室的 recipe、执行列表（倒序、limit、限定腔室）、不存在 404。
      
    
      名称与机台类型PATCH 只改传入字段、清空、404；列表按 tool_type 过滤、q 匹配显示名称；tool-types 去重。
      
    
      下线算子下线生成空 system 修订、撤回 pending、取消不再需要的订阅；特征整体下线带下全部已发布算子。
      
    
      LiveConsumer（fakeredis + FakeGdeClient）同一消息投递两次只写一次；GdeUnavailable 不 ACK、认领后重试成功；超过投递上限写 FETCH_ERROR；配方不在绑定内直接 ACK；实时批次按整点归并。
      
    
      BatchRunnerfill 跳过已有值、覆盖该 recipe 下全部腔室；overwrite 覆盖并标记旧批次 superseded_by；cancel 生效；两个实例不会领同一个批次。
      
    
      端到端真实 PostgreSQL + fakeredis + FakeGdeClient：新增特征 → 他人评审 → 新增算子 → 试跑 → 他人评审 → 按算子绑定 → 他人审核 → 向 Stream 写一条通知 → 在 /api/values 查到值，且能追溯到批次和算子 code_hash。
